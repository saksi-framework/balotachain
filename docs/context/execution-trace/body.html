How to read this

The eight steps below are a genuine sequence — each one depends on the last, and the numbering carries that. Steps 1 to 7 follow one election; step 8 runs ten of them as precincts on one channel, on a later build, and canvasses their signed returns into a national result. Paths are repo-relative: saksi/** is the framework, balotachain/** the thesis repo with the browser apps. The console lives in saksi/packages/saksi-campaign/, and every Go file named without a directory sits there.

Two structural ideas are worth holding on to. The Go layer never implements protocol logic: it orchestrates, submits to the ledger and shells out to the Rust binary for anything cryptographic, so the auditor is a different program reading published files. And the console is a research harness: it generates the whole voter population and every ballot itself. No route lets a person cast their own ballot; live voting is outside what this code does.

runs once: election parameters, the DKG transcript and the credential issuer's keypair. Then voters are built 5,000 per chunk, the chunk's voters in parallel, and written in voter order before the next chunk starts — so memory is bounded by a chunk, not the population.

Every voter's choice comes from one deterministic rule. There is no seed: restating the generation parameters reproduces the population exactly. The realistic profile is the only one that decides an election — uniform ties at rank one by construction, and skewed leaves every loser on an identical count.

The reserved slice is then apportioned down the ranks, which separates the candidates the round-robin left level. All of it is integer arithmetic — floating point would make the population depend on the machine's rounding.

Per voter, runs the real cryptography: a blind-signed credential (saksi-credentials/src/issuance.rs), an ElGamal ciphertext per candidate under the joint DKG key (saksi-crypto/src/elgamal.rs), a CDS OR-proof per ciphertext that it encrypts 0 or 1 (saksi-crypto/src/nizk/cds.rs), and a per-position nullifier (saksi-credentials/src/nullifier.rs) — which is what makes double voting detectable without linking a ballot to a voter.

The published tally carries a Schnorr signature per trustee over the exact totals. keeps only the signatures of the trustees who actually submitted, so the ledger's count reflects the ceremony that happened, not the full set the generator could produce.

Where the threshold is enforced. In three places now. The console refuses to publish below t (409; since saksi #57 the wizard's trustee ceremony shows that refusal and its reason). The chaincode's refuses a tally unless every signature verifies and at least t distinct trustees signed. The auditor re-proves it at step 6 (decryption.threshold, tally.signatures). What the chaincode still does not check is the Chaum-Pedersen proof on each partial decryption: requires it to be present (gate cp-presence), and only the auditor verifies it.

A real election, opened up

Everything below is decoded from one actual run on the pinned commit — halalan-2026-20261015-113840-2, the offline election reported under Verified end to end. These are its real bytes, decoded with the repo's own cmd/dumpwire. Long values are shortened in the middle as head…tail; nothing else is altered.

The point of reading it this way: most of these blobs are not encrypted at all. They are protobuf, hex-encoded for transport. Only a few fields actually hide something, and it is worth knowing exactly which.

Worth settling before the tables, because hex usually means a digest: none of these blobs is a hash. Protobuf wire encoding is reversible and the bytes carry the field values in the clear — which is exactly why cmd/dumpwire can read a run's artifacts back. Take the first four bytes of params: 08 is (field 1 << 3) | 0, a varint, so 08 01 is version = 1; 12 is field 2, length-delimited, 1e is 30, and the next 30 bytes spell halalan-2026-… in ASCII. The plain chips mean it.

So each artifact below is given three ways: what its fields mean, then the complete value as stored, then where each field physically sits in that value. Offsets are byte positions from the start of the blob, and every byte is accounted for — wirebreak.py walks each artifact and exits non-zero if one byte is left over, because a partial decode drawn as a tidy table would misrepresent the artifact. Repeated fields are listed twice and then collapsed, with the elided row still carrying the bytes it stands for, so the offsets either side of it still add up.

The two digests that matter most. ballots_sha256 pins the encrypted set an audit ran against, and ground_truth_ballots_sha256 pins the plaintext population it was built from. The encryption is randomised, so ciphertexts can never link a run back to its population — these digests are what does.

Where they come from, precisely. Not from header.json: none of these digests is a field on the wire. The console computes them itself — (saksi/packages/saksi-campaign/csvexport.go, lines 113–129) hashes the decoded ballot bytes in file order, gathers the set, and they are surfaced as the dkg_sha256, tally_sha256 and ballots_sha256 columns of election.csv. ground_truth_ballots_sha256 is written by the validation gate into ground-truth-check.json. Serialising a value is not protecting it. The question that matters for the panel is narrower: if someone edits this field, what breaks? The same bytes get different guarantees in the two verifiers. The chaincode checks the CDS proof, the issuer signature and the tally signatures at endorsement. It does not check the Chaum-Pedersen proof tying a credential to its nullifier, the position_id binding, the Chaum-Pedersen proof on each partial decryption — requires only that a proof is present, gate cp-presence — or the homomorphic sum. All four are the auditor's alone. That is the precise, checkable form of "the chain validates shape, the auditor validates the mathematics".
One context builder is the exception. concatenates the election id and the totals without length prefixes, unlike every other context in this codebase. An election id ending in eight attacker-chosen bytes could therefore be read as absorbing a total. The code says so itself and rests the argument on the id being fixed at deployment; it is noted here rather than left for a reader to find.

Values stored on the blockchain

Everything above is decoded from the run's files. This is the other half of the question: what a Fabric peer actually holds in world state once the same election has been driven onto the ledger. The two sets overlap but are not the same — the header carries generation metadata the chaincode never sees, and the chain carries a per-ballot key the header never writes.

Every entry is a Fabric composite key, built the same way each time: "\x00" + objectType + "\x00" + attr + "\x00", one attr segment per key attribute, in the order given below. A ballot therefore lives at \x00ballot\x00<electionID>\x00<nullifierHex>\x00, and nothing but the object type separates one family of records from another.

Two of those are worth pausing on. The ballot and nullifier families share a key shape, which is what makes the double-vote check a single GetState rather than a scan: the nullifier marker is written in the same transaction as the ballot it belongs to. And the nullifier value carries no information at all — one byte, present or absent. Every field an app needs about a ballot is read from the ballot record itself.

Not on the chain. The election name and the trustee names; binding_context (saksi-auditor-v1) — it domain-separates every NIZK in the run, but the chaincode never stores or checks it; the header's issuer_pk field — the per-ballot issuer_public_key is stored inside every ballot record, but at the pinned commit nothing on the chain says which issuer the election trusts, so a ballot under a self-issued credential was accepted and only the auditor's ballot.issuer_binding, reading the header, could catch it (since saksi #55 the election parameters carry the issuer key and SubmitBallot refuses any other at gate issuer); n; ground_truth[]; voter_ids[]; the order of the ballots — records are keyed by nullifier, so world state holds a set and not a sequence; and every digest — ballots_sha256 and its siblings are computed by the console after the fact and never written to state.

Two absences of a different kind. No caller identity is recorded: no contract function calls GetClientIdentity, so the ledger says what was submitted and never who submitted it. And nothing is ever deleted: DelState appears nowhere in the chaincode, and every write guards against overwriting an existing key.

Alongside its own state, Fabric records the transaction that produced it. The SDK reads that back as a receipt, one per committed ballot:

Receipt fieldWhat it is
TxIDthe transaction id the submission was endorsed under
BlockNumberthe block it committed in

Two things a receipt is not. Fabric stores no block hash on the block, so recomputes it from the header — a receipt's BlockHash is derived by the reader, not fetched. And Timestamp is when the client proposed the transaction, so it is a client clock, not an ordering guarantee; BlockNumber is the only ordering the ledger itself asserts.

The run decoded above was offline. It has no receipts, no block numbers and no transaction ids, because no peer was involved. Every on-chain figure quoted later on this page comes from the recorded WSL run, and is cited as such.
What step 8 adds on chain: nothing new. Each precinct is an ordinary election — cv-m1-p01 to cv-m1-p10 — so the ten write the same key families above under their own election ids, all on the one channel saksi. A precinct return is a signed file, not a transaction: and sit in the chaincode's sigverify package, but no contract function calls them. The close block and tip hash a return binds are read from the channel through (qscc), not written to it.

One attack at a time: clean vs tampered

Step 7 named the gates. This is what they actually refused, byte by byte, in the run decoded above. works the same way every time: copies header.json and ballots.ndjson into scenarios/<id>/, the untouched copy is audited first as a positive control, exactly one mutation is applied — through for a header field, or in place for a ballot line — and the copy is audited again. then reads the auditor's failed checks and decides the verdict, and records it. The real election is never touched: every figure below is a diff against a copy.

Four of the six mutations change a single byte, and in three of those it is a single flipped bit — ^= 0x01 on the first byte of a proof response or a commitment. That is the point of the exercise: the smallest edit the format allows is still refused, and refused by the check it was aimed at rather than by something downstream noticing later.

Declared limitations

Recorded rather than discovered — each is stated here as it is in the code.

Runs generated before saksi #50 used fixed DKG dealers. Their election keys can be derived from the source, so they support correctness, verifiability and performance results, not ballot secrecy. From that change on, every dealer polynomial is random.
The ceremony is simulated. The generator produces every partial decryption and signature in one process; the console forwards them when a trustee acts, so that one process holds every key share. The cryptography is real; separation between trustees is not exercised.
The chaincode does not authorise callers. No contract function reads the caller's identity, so anyone with a channel identity could create an election under a chosen id first, or submit to one — a front-running denial of service, not a forgery: every submission still passes the same gates.
Ordering is still not detected on the published file. saksi #58 added , and reports check ledger.order — but it is narrower than its name suggests, and the measurement says so. It asks whether the chain's read-back is in canonical nullifier order, and it sorts the served records before comparing, so a reordered ballots.ndjson yields the same digest as the clean one. Measured on this run: swapping lines 1 and 2 still audits pass with failed_checks: []; with a canonical ledger/ dump present the digest is byte-identical either way; only permuting the chain read-back dump itself makes ledger.order fail. Nothing in the chaincode checks sequence at all. This is why reordered-ballots is still SKIPPED with "no gate exists to test". Reordering cannot change a result — the tally is order-independent by construction — but it remains invisible in the published record, and that is the honest statement.
Chaum-Pedersen proofs are checked for presence on-chain. A share with a wrong proof is recorded by the ledger and caught only by the auditor.
Contest-mixing is narrowed, not closed. The three positions usually differ under realistic, but in roughly 8.6% of configurations they land on the same multiset of totals. On those, E = 0 could not tell one contest from another.
One vote per position. Multi-seat races are decided by plurality over a single selection each (single non-transferable vote). Since saksi #55 a Chaum-Pedersen selection_proof shows each record's ciphertexts sum to exactly one, so an overvote is refused on-chain at gate selection rather than only noticed by the auditor. Letting a voter mark N candidates for one position would need the same proof generalised to sum to N — new cryptography, not configuration. Note also that the gate is conditional: it runs only when the election parameters carry an issuer_public_key, so an election created before saksi #55 skips both it and the issuer gate.
One machine, not independent organisations. The chaincode has no DelState and guards every write against overwrite, so the record is append-only. But the test network's two organisations and single orderer run on one computer; distributed immutability needs independent operators.
No live voter. Ballots come from the generator, and no route accepts a ballot cast by a person. The Flutter voter app reaches the console only to check a tracking code (ReceiptVerifyScreen → GET /api/verify-code/<run>/<code>).
The precinct canvass (step 8) has four limits. Detection, not refusal: the canvass is verifier-side, so T15, T16 and T24b are committed, then detected; only the two attacks on the shared channel, T19 and T20, are refused, by the chaincode's election binding. One machine, one channel: the ten precincts share channel saksi on one test network, and the transmission path is a file copy, not a network. Simulated authorities: one program generated every precinct authority key, so a compromised precinct (malware) is modelled by using its real key. A later build: saksi 0cdc335, 10,000 voters in the clean runs and 1,000 in each attack run, with throughput and latency bound by the batch timeout; never compared with the study tiers, and the SP and MP study runs are not precinct runs.

Delay or loss on the path (T17) and capture of returns in transit (T18) need a network this build lacks; both are deferred to the size L design.
