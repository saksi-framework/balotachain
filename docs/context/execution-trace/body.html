How to read this

The seven steps below are a genuine sequence — each one depends on the last, and the numbering carries that. Paths are repo-relative: saksi/** is the framework, balotachain/** the thesis repo with the browser apps. The console lives in saksi/packages/saksi-campaign/, and every Go file named without a directory sits there.

Two structural ideas are worth holding on to. The Go layer never implements protocol logic: it orchestrates, submits to the ledger and shells out to the Rust binary for anything cryptographic, so the auditor is a different program reading published files. And the console is a research harness: it generates the whole voter population and every ballot itself. No route lets a person cast their own ballot; live voting is outside what this code does.

2Ballots

Generate the population, then encrypt it

Stage 4 of the methodology. The Go layer opens the run's journal and builds an argv; the Rust binary does the work, a chunk of voters at a time.

runs once: election parameters, the DKG transcript and the credential issuer's keypair. Then voters are built 5,000 per chunk, the chunk's voters in parallel, and written in voter order before the next chunk starts — so memory is bounded by a chunk, not the population.

Every voter's choice comes from one deterministic rule. There is no seed: restating the generation parameters reproduces the population exactly. The realistic profile is the only one that decides an election — uniform ties at rank one by construction, and skewed leaves every loser on an identical count.

The reserved slice is then apportioned down the ranks, which separates the candidates the round-robin left level. All of it is integer arithmetic — floating point would make the population depend on the machine's rounding.

Per voter, runs the real cryptography: a blind-signed credential (saksi-credentials/src/issuance.rs), an ElGamal ciphertext per candidate under the joint DKG key (saksi-crypto/src/elgamal.rs), a CDS OR-proof per ciphertext that it encrypts 0 or 1 (saksi-crypto/src/nizk/cds.rs), and a per-position nullifier (saksi-credentials/src/nullifier.rs) — which is what makes double voting detectable without linking a ballot to a voter.

writes header.jsonballots.ndjson gen-timings.jsonground-truth-ballots.csv ground-truth-summary.csvballots.csv election.csvjournal.ndjsonrun.json
The separation that gives E = 0 teeth. Selections are recorded explicitly and the ground truth is computed from that, by — never accumulated as a side effect of building ciphertexts. If it were, a crypto bug that encrypted the wrong value would corrupt both sides equally and the check would still pass.
Every dealer polynomial is drawn from the OS random generator. Each trustee's coefficients come from , so the joint secret key of a generated election cannot be derived from this public source, and two elections with identical parameters get unrelated keys. Until saksi #50 the coefficients were fixed at dealer_id × 13 + k + 1: runs generated before that change support correctness, verifiability and performance results, not ballot secrecy.

5Trustees

Threshold decryption

The election is closed and its tally encrypted. It stays that way until t of n trustees act — the system's central custody claim.

The published tally carries a Schnorr signature per trustee over the exact totals. keeps only the signatures of the trustees who actually submitted, so the ledger's count reflects the ceremony that happened, not the full set the generator could produce.

Where the threshold is enforced. In three places now. The console refuses to publish below t (409). The chaincode's refuses a tally unless every signature verifies and at least t distinct trustees signed. The auditor re-proves it at step 6 (decryption.threshold, tally.signatures). What the chaincode still does not check is the Chaum-Pedersen proof on each partial decryption: requires it to be present (gate cp-presence), and only the auditor verifies it.

The auditor never short-circuits. Ballots are verified in batches of 4,096, in parallel on every core (SAKSI_AUDIT_THREADS); everything that depends on order — findings, first use of each nullifier, the aggregate — is folded serially in stream order, so the result is byte-identical to a one-thread run. This is where the ciphertexts become a result. Eligible ballots are summed point-wise per contest as they stream past — the reason ElGamal was chosen:

Then the trustee shares are combined by Lagrange interpolation at zero and the plaintext point is turned back into a number. Because the count is a small integer, that is a discrete log over a bounded range — baby-step giant-step from 50,000 up, linear below:

Each contest's E = T − G, the decoded total minus the seeded ground truth, must be zero. correctness.csv also carries the recovered point, the aggregate ciphertext it came from, and the run's artifact hashes — and for an on-chain run a second block of rows, source=ledger, with the ledger_matches_local verdict. then decides run.end: a stage error, nothing submitted, a dropped ballot, a reconcile mismatch, any E ≠ 0, or an interruption fails the run.

Attack it, and name the gate that refused

Step 6 shows an untouched election decrypts correctly. This shows a tampered one is rejected — by the check it was aimed at, not by accident.

Simulated, an attack mutates a copy of the run and re-audits it, after first auditing the unmutated copy as a positive control; then reads the auditor's failed checks. Live, only the three ballot attacks have a chaincode gate to test: they are submitted to the open election at the ballots pause, and reads the gate=<id>: prefix of the peer's refusal.

So there are four verdicts: PASS when the declared gate refused it, INCONCLUSIVE when something else did (or the positive control failed), FAIL when the tampered artifact was accepted — a genuine finding — and SKIPPED when no gate exists to test. The wizard's attack step runs the catalogue simulated; the live mounts happen at the pause points of a security run.

writesscenarios.json negative-tests.csv
Why the gate id matters. The chaincode refuses at the first check a submission fails. A tampered proof sent to a closed election is refused as “not open for ballots” and never reaches the proof check. Scoring that as a pass for the proof gate was how earlier on-chain verdicts overstated what they showed; those rows were discarded, not re-used.

A real election, opened up

Everything below is decoded from one actual run on the pinned commit — halalan-e2e-20260915-063540-1, the offline election reported under Verified end to end. These are its real bytes, decoded with the repo's own cmd/dumpwire. Long values are shortened in the middle as head…tail; nothing else is altered.

The point of reading it this way: most of these blobs are not encrypted at all. They are protobuf, hex-encoded for transport. Only a few fields actually hide something, and it is worth knowing exactly which.

The two digests that matter most. ballots_sha256 pins the encrypted set an audit ran against, and ground_truth_ballots_sha256 pins the plaintext population it was built from. The encryption is randomised, so ciphertexts can never link a run back to its population — these digests are what does.

Where they come from, precisely. Not from header.json: none of these digests is a field on the wire. The console computes them itself — (saksi/packages/saksi-campaign/csvexport.go, lines 113–129) hashes the decoded ballot bytes in file order, gathers the set, and they are surfaced as the dkg_sha256, tally_sha256 and ballots_sha256 columns of election.csv. ground_truth_ballots_sha256 is written by the validation gate into ground-truth-check.json. Hashing in file order is the detail that matters later: see the reordered ballots.
plain Readable once de-hexed. Carries no secret and is not meant to.
ciphertext An ElGamal pair. Hides a value only a threshold of trustees can recover.
commitment Binds to a value without revealing it.
proof Zero-knowledge — reveals nothing beyond the truth of one statement.
one-way tag A PRF pseudonym. Catches a repeat; never points back to a person.
signature A Schnorr signature: anyone can check it, only the key holder could make it.

Values stored on the blockchain

Everything above is decoded from the run's files. This is the other half of the question: what a Fabric peer actually holds in world state once the same election has been driven onto the ledger. The two sets overlap but are not the same — the header carries generation metadata the chaincode never sees, and the chain carries a per-ballot key the header never writes.

Every entry is a Fabric composite key, built the same way each time: "\x00" + objectType + "\x00" + attr + "\x00", one attr segment per key attribute, in the order given below. A ballot therefore lives at \x00ballot\x00<electionID>\x00<nullifierHex>\x00, and nothing but the object type separates one family of records from another.

objectTypeKey attributesValue storedWritten byRead by
election [electionID] ElectionParameters — version, election_id, contest_ids[], trustee_ids[], threshold
status [electionID] the bytes open or closed — nothing else ·
dkg [electionID] DKGTranscript — threshold, trustee_commitments[], complaints[]
ballot [electionID, nullifierHex] the entire submitted Ballot — ciphertexts, CDS proofs, credential commitment, issuer public key, presentation proof, nullifier ·
nullifier [electionID, nullifierHex] the single byte 0x01 — a spent marker, no payload
partialdec [electionID, contestID, trusteeID] PartialDecryption — trustee_id, share, proof, contest_id
tally [electionID] TallyResult — totals[], partial_decryptions[], signatures[]

Two of those are worth pausing on. The ballot and nullifier families share a key shape, which is what makes the double-vote check a single GetState rather than a scan: the nullifier marker is written in the same transaction as the ballot it belongs to. And the nullifier value carries no information at all — one byte, present or absent. Every field an app needs about a ballot is read from the ballot record itself.

Not on the chain. The election name and the trustee names; binding_context (saksi-auditor-v1) — it domain-separates every NIZK in the run, but the chaincode never stores or checks it; the header's issuer_pk field, though the per-ballot issuer_public_key is stored inside every ballot record, so eligibility stays checkable from the chain alone; n; ground_truth[]; voter_ids[]; the order of the ballots — records are keyed by nullifier, so world state holds a set and not a sequence; and every digest — ballots_sha256 and its siblings are computed by the console after the fact and never written to state.

Two absences of a different kind. No caller identity is recorded: no contract function calls GetClientIdentity, so the ledger says what was submitted and never who submitted it. And nothing is ever deleted: DelState appears nowhere in the chaincode, and every write guards against overwriting an existing key.

Alongside its own state, Fabric records the transaction that produced it. The SDK reads that back as a receipt, one per committed ballot:

Receipt fieldWhat it is
TxIDthe transaction id the submission was endorsed under
BlockNumberthe block it committed in
BlockHashSHA-256 over the ASN.1-DER block header — recomputed, see below
DataHashthe hash of the block's transaction payload, as stored
PreviousHashthe previous block's header hash — the chain link itself
Timestampthe proposal time carried in the transaction, not the commit time
Two things a receipt is not. Fabric stores no block hash on the block, so recomputes it from the header — a receipt's BlockHash is derived by the reader, not fetched. And Timestamp is when the client proposed the transaction, so it is a client clock, not an ordering guarantee; BlockNumber is the only ordering the ledger itself asserts.

The run decoded above was offline. It has no receipts, no block numbers and no transaction ids, because no peer was involved. Every on-chain figure quoted later on this page comes from the recorded WSL run, and is cited as such.

One attack at a time: clean vs tampered

Step 7 named the gates. This is what they actually refused, byte by byte, in the run decoded above. works the same way every time: copies header.json and ballots.ndjson into scenarios/<id>/, the untouched copy is audited first as a positive control, exactly one mutation is applied — through for a header field, or in place for a ballot line — and the copy is audited again. then reads the auditor's failed checks and decides the verdict, and records it. The real election is never touched: every figure below is a diff against a copy.

Four of the six mutations change a single byte, and in three of those it is a single flipped bit — ^= 0x01 on the first byte of a proof response or a commitment. That is the point of the exercise: the smallest edit the format allows is still refused, and refused by the check it was aimed at rather than by something downstream noticing later.

The attack that succeeds: reordered-ballots

Six of the seven scenarios are refused. One is not, and it is not refused because nothing refuses it. reordered-ballots swaps two ballot lines and leaves every gate on the page satisfied.

It produces no scenarios/ folder at all: sees a chaincode-layer scenario with no chaincode gate to test and returns SKIPPED before makes the copy. So there is nothing on disk to diff, and the comparison below was built by hand: header.json copied unchanged, lines 1 and 2 of ballots.ndjson swapped — exactly what the scenario registry describes — and both copies then audited with the real saksi-demo audit-stream --json.

That contrast is the whole mechanism. hashes the decoded ballot bytes in file order, so a swap moves it. The digests the ledger comparison actually uses — and — are order-independent by construction, which is precisely why would call the reordered copy the same election as the clean one.

What this does and does not show. Reordering changes the provenance fingerprint the console records, and nothing that any verifier checks. The auditor passes it with no failed checks, the tally is identical to the vote, and the chaincode has no ordering gate to refuse it with. It is worth being exact about the consequence: nobody's vote changes, no vote is added or lost, and no result moves. What is lost is the ability to say that the file in front of you is the file that was written — a provenance claim, not a correctness one. This is the declared limitation corrected in saksi #45, restated here with its bytes; it is not a new finding.

Declared limitations

Recorded rather than discovered — each is stated here as it is in the code.

Runs generated before saksi #50 used fixed DKG dealers. Their election keys can be derived from the source, so they support correctness, verifiability and performance results, not ballot secrecy. From that change on, every dealer polynomial is random.
The ceremony is simulated. The generator produces every partial decryption and signature in one process; the console forwards them when a trustee acts, so that one process holds every key share. The cryptography is real; separation between trustees is not exercised.
The chaincode does not authorise callers. No contract function reads the caller's identity, so anyone with a channel identity could create an election under a chosen id first, or submit to one — a front-running denial of service, not a forgery: every submission still passes the same gates.
Ordering is not detected. Swapping ballot lines changes nothing any verifier checks, so reordered-ballots is always SKIPPED.
Chaum-Pedersen proofs are checked for presence on-chain. A share with a wrong proof is recorded by the ledger and caught only by the auditor.
Contest-mixing is narrowed, not closed. The three positions usually differ under realistic, but in roughly 8.6% of configurations they land on the same multiset of totals. On those, E = 0 could not tell one contest from another.
One vote per position. Multi-seat races are decided by plurality over a single selection each (single non-transferable vote). A ballot marking several candidates for one position needs a proof that selections sum to N — new cryptography, not configuration.
One machine, not independent organisations. The chaincode has no DelState and guards every write against overwrite, so the record is append-only. But the test network's two organisations and single orderer run on one computer; distributed immutability needs independent operators.
No live voter. Ballots come from the generator. The Flutter voter app is not connected to the console, and no route accepts a ballot cast by a person.
