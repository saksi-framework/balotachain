# Chapter 4 study, Night 1: SP-1M (row 6) on saksi `4a38a54`: incomplete, host disk full

Executed 2026-10-01 05:42–07:57 local time (2026-09-30 21:42–23:57 UTC) on the Ryzen desktop under WSL2, as Night 1 item 4 and run-table row 6: 1,000,000 voters x 1 position, the provincial-scale stress test. It ran as **0 warm-ups + 3 measured**. The user's decision (2026-10-01): "no warm-up at 1M+; a start-up effect is negligible over an election that long; user decision 2026-10-01 to shorten night 1". Election name `SP-1M ch4`. Night index: [`2026-10-01-night1.md`](2026-10-01-night1.md).

**Outcome.**
- **One valid measured repetition.** m1 committed all 1,000,000 ballots at **428.3 TPS** with E = 0.
- m2 lost its last 67,300 ballots, and m3 could not start.

Both failures have one cause: **the host drive Q: filled up.** Docker's data disk is a dynamically expanding VHDX on Q:, and it holds all the Fabric volumes. At 07:34 local it could not grow, the WSL guest took the disk offline, and the peer died with SIGBUS. This is an environment failure, not a protocol or chaincode finding. It is still a real resource limit of this desktop, and the paper should state it (§5). Row 6 needs a rerun after the disk is cleared.

Artifacts are in `docs/desktop-runs/2026-10-01-sp-1m/`: the campaign export, unzipped (`summary.csv`, `campaign.json`, `preflight.json`, `MANIFEST.txt`, the three run folders' files), and `campaign-log.txt`. The peer and orderer `docker logs` could not be saved: Docker's API answered 500 after the disk went offline. There is no `ledger-size.txt` for the same reason.

## 3. What happened in m2 and m3

**m2.** Ballots committed normally at about 413 TPS up to index 932,678. The `ballots.progress` checkpoints show a 12.7 s gap at 932,000 → 933,000, ending at 23:34:33Z. From index 932,679 to 999,999 every ballot is a `drop` in `latencies.csv`, each after about 10.65 s, and the closed-loop window drained the rest as failures (the pattern seen in T3). The journal has 18,654 `receipts.missing` events. The verify stage skipped the ledger dump (`ledger_audit` "not run"). The local tally of the generated ballots is still E = 0, but there is no ledger comparison.

**m3** failed at its first chaincode call: peer0.org1 refused connections.

**Root cause: the host disk.** The WSL kernel log (`dmesg`), at uptime 23,045–23,055 s (07:34:05–07:34:15 local, 23:34Z):
- `hv_storvsc … cmd 0x2a status: scsi 0x2 …`: SCSI WRITE(10) failures;
- `sd 0:0:0:2: Device offlined - not ready after error recovery`;
- `I/O error, dev sdc, … op 0x1:(WRITE)`, `EXT4-fs (sdc): failed to convert unwritten extents to written extents -- potential data loss!`;
- `peer: potentially unexpected fatal signal 7` (SIGBUS), and the same in `chaincode` and `containerd-shim`.

`sdc` is Docker's data disk, mounted in the peers at `/var/hyperledger/production`. `C:\Users\User\AppData\Local\Docker\wsl\disk` is a junction to `Q:\DockerDesktop\DockerDesktopWSL\disk`, where `docker_data.vhdx` measured **216.8 GB** afterwards. `Get-Volume` showed **Q: with 0 GB free** of 931 GB, and C: with 19 GB. The physical disks report Healthy.

Q: had about 122 GB free at the start of the night (WSL `df /mnt/q`). The night added about 100 GB of Fabric data, for two reasons:
- **every ledger is stored three times** (peer0.org1, peer0.org2, the orderer): SP-483K alone left 28.1 + 28.1 + 23.4 GB;
- a network reset frees space inside the VHDX but does not shrink the VHDX file.

So the VHDX could not grow during m2, about 1.93M records into the SP-1M network (m1 plus 932,700 of m2).

**Why the preflight did not catch it.** The Disk row measures the run store's volume inside WSL, not the Docker disk (runbook §10.3). The guest `df` of the peer volume shows the VHDX's virtual size, 1 TB, not the host space behind it. The driver logged the latter as "930 GB free" before the night. The real limit was Q:'s free space, which nothing checked.

## 5. Caveats and what it means for the paper

- **Row 6 has one valid repetition, not three.** It is reported as a single sample, with m2 and m3 as an infrastructure failure. A rerun on a cleared disk is needed for 3 measured repetitions.
- **Disk is a binding resource at the capstones.** On-chain storage is about 11.9 KB per ballot record per copy (SP-483K note §6). This test network keeps three copies, about 36 KB per record, so:

  | Tier | Fabric data |
  |---|---|
  | SP-1M | ~36 GB per election |
  | SP-1.92M | ~69 GB |
  | SP-3.5M | ~127 GB |
  | MP-3.5M on-chain | ~380 GB |

  The plan's "~127 GB" for MP-3.5M on-chain is per copy. The VHDX must also be compacted, or the host drive must have room for every election run since the last compaction.
- m2's 412.8 TPS over its first 932,700 ballots was not affected by the disk until the end, but the run failed and is excluded from every statistic.
