## 2. Proof that both changes took

**Orderer parameters — from the ledger, not the config.** Distinct `block_number`
values over the `SubmitBallot` rows of `receipts.csv`: every one of the 10,000 ballots
of the first on-chain run (`p2-sp-10k-c128-20260911-115408-1`) sits in one of **200
blocks of exactly 50** (`uniq -c` over the per-block counts returns the single line
`200 50`). On the test-network default the same workload gives 1,000 blocks of 10. The
same holds in every rep of every tier below (`ballots_per_block` = 50.0 in every
`stages.json`, `max_per_block` = 50 in every `stall.csv` row).

**PR #38's batched read path — from the journal.** `executor.go`'s `auditLedger`
stamps a `ledger.dump` record with the read path that served the chain dump
(`"batched"` = `GetBallots` pages of 500; `"per-ballot"` = a chaincode that predates
it). From the same first run, verbatim:

```json
{"ballots":10000,"event":"ledger.dump","mono_ms":4671,"ok":true,"read_path":"batched","ts":"2026-09-11T11:54:42Z"}
```

`read_path` is `batched` in every run of this session. The record is stamped when the
dump returns, 4,671 ms into the verify stage (`mono_ms` restarts per console phase), so
dumping 10,000 ballots from the chain now costs under 0.5 ms/ballot.

**PR #38's concurrent partial decryptions — from the receipts.** The lifecycle tail
(`CloseElection` → `PublishTally`) is **6 s** for SP and **10 s** for MP in every rep,
against 42.5 s and 123 s in the row-2 runs, where each of the 20 / 60
`SubmitPartialDecryption` transactions sat alone in its own block and waited out the
2 s `BatchTimeout`. The partials now share blocks.

on-chain), one measured rep per step, no warm-ups, **a fresh channel (`tier.sh 10000 1`)
and a restarted console before every step**, so no step pays for an earlier step's
ledger. The c = 96 and the first c = 192 rows are reused from the orderer probe
(`2026-09-11-orderer-probe.md` §3, `b50-t2s`, same NVMe storage, saksi `3cb07fc`: PR #38

**The rule.** c = the **lowest** concurrency whose `committed_tps` is within 15 % of the
best observed **and** whose p99 is under 1 s **and** which shows zero block gaps ≥ 3 s.

Best observed = 1005.88 (c = 192, orderer probe), so the throughput bar is
0.85 × 1005.88 = **855.0 TPS**. In ascending order: c = 96 fails it (812.01); **c = 128
clears all three** (926.05 TPS, p99 241.6 ms, 0 gaps). **Chosen: c = 128.**

The pick does not depend on which c = 192 row is taken as "best": counting only this
probe's `cf9fd2a` rows, the best is c = 384 (966.79), the bar 821.8, and c = 128 is still
the lowest step to clear it (c = 96's 812.01 fails either bar).

What the table shows beyond the pick: from c = 128 up, throughput is one plateau of
~800–1,000 TPS with single-rep noise as large as the differences between steps — the
two c = 192 reps, same parameters, same disk, differ by 15 % (1005.88 vs 853.37) — while
latency grows in proportion to the in-flight count (p50 ≈ c / tps: 128 / 926 = 138 ms
against a measured 147; 384 / 967 = 397 ms against 393). Past the plateau's entry, extra
concurrency buys queueing, not throughput. c = 128 is that entry: full throughput at the
lowest latency, and 2.6 × `MaxMessageCount`, so every block fills (the orderer probe's
caveat — `MaxMessageCount` 50 needs ≥ 50 in flight — holds with margin).

## 4. How every tier was run

Per tier: `tools/tier.sh <voters> <positions>` (network down, fresh channel generated
from the adopted `configtx.yaml`, chaincode redeployed — an empty ledger), the console
restarted in tmux `console` and `up.sh status` waited on until it reported on-chain
ENABLED (`{"fabric":true,"peer":"localhost:7051","channel":"saksi"}` reconfirmed), then

```
saksi-campaign --repeat --config ~/rows24/<tier>-b50.json \
    --warmups <W> --reps <R> --out ~/rows24/<tier>-b50-summary.csv
```

Each config is `~/sp-1k.json` with `name` = `<tier>-b50`, `voters`, `positions` and
`concurrency: 128` set: 5 trustees, threshold 3, 4 candidates, `realistic`, `onchain`.
The driver is `~/rows24/rows.sh 128`, one tmux session (`rows`), log
`~/saksi-logs/rows.log`. After each tier, `stats.sh` (the orderer probe's, unchanged)
wrote one stall-evidence row per rep and `stages.py` one `stages.json` per rep.

A **stall** is a measured rep with p99 > 5 s (the brief's definition). A **slow rep** is
one with 1 s < p99 ≤ 5 s — reported, not counted as a stall. `scaling_limit` is `false`
exactly on the reps whose `committed_tps` fell below 0.8 × `driver_ceiling_tps` (the
reps where the network, not the harness, set the rate) and `inconclusive` on the rest.
Medians in the field tables are `summary.csv`'s own, which takes the lower of the two
middle values for n = 10 (so 948.479 for SP-1K, where the interpolated median would be
971.5) — the same convention as the row-2 note, so the before/after in §8 compares like
with like.

## 9. Cost model, refitted on these runs

`docs/desktop-runs/cost-model.md` is regenerated by `cost_model.py` from **the rows 2–4
runs of this note only** (62 folders: 50 measured reps, and 12 warm-ups the script
excludes), plus the one true-offline run for row 8:

```
python3 docs/desktop-runs/cost_model.py \
    --runs /home/user/.saksi/campaign/runs --runs /home/user/.saksi/campaign/runs-offline \
    --match 'sp-*-b50-*' --match 'mp-*-b50-*' --match 'offline-*' \
    --fit-concurrency 128 --out docs/desktop-runs/cost-model.md
```

Two changes to `cost_model.py` were needed for it to fit these runs honestly, both small:

1. **Run selection.** The WSL runs tree holds every regime measured so far (default and
   `b50-t2s` parameters; `302d569`, `3cb07fc` and `cf9fd2a` builds). A new repeatable
   `--match GLOB` reads only folders whose name matches, and the script now **refuses to
   fit** when one cost class spans more than one regime — a regime being (auditor
   `verify_threads`, absent = 1; `orderer_batch` from `journal.ndjson` line 1, absent =
   not recorded; saksi commit from `run.json`). Refusing, rather than fitting per group,
   was chosen because every coefficient — not only the audit term — can move between
   regimes, and `v_dump` is derived as verify minus audit and would inherit any shift.
   These runs predate `orderer_batch`, so the orderer configuration is not in the
   automatic key: within one commit it is separated by name pattern only (`*-b50-*`),
   which is why the invocation above uses `--match`. The unfiltered tree is refused with
   a message naming the three regimes it holds.
2. **The lifecycle term.** `L(p) = tau × (4 + trustees × p × candidates)` assumed one
   lifecycle transaction per block. Since PR #38 the partials share blocks, the median
   receipt gap `tau` is 0, `L` drops out, and the lifecycle's six or eight
   `BatchTimeout`-bound blocks (§8) land in `c0`. The script now says so in its output
   instead of describing the pre-#38 lifecycle, and its prose no longer hard-codes the
   default orderer parameters or the 15 GB allotment. `--selfcheck` covers the regime
   guard; it passes.

## 10. Caveats and what the instrument refused

- **Single-rep probe.** Each probe step is one rep; the two c = 192 reps differ by 15 %.
  The pick (c = 128) is robust to that (§3), but the probe's per-step TPS values are
  indicative, not citable. The citable figures are the rows' medians over 10 (or 5) reps.
- **`scaling_limit` is never `true`.** It is `inconclusive` on every rep where
  `committed_tps` sits within 20 % of `driver_ceiling_tps` and `false` on the five reps
  below 0.8 × the ceiling (SP-10K 2, MP-10K 2, MP-50K 1; §§6–7). 800–950 TPS is what this
  network sustained under a closed-loop driver at c = 128, not a proven system ceiling.
- **`peak_cpu_pct_*` are empty for SP-1K and MP-1K** — windows of 1–3 s, a 5 s sampler.
  From 10K up they are populated: the peer peaks at 4.6 cores (463 %, MP-50K) and the
  orderer at 1.0 (103 %), of 16 — the CPU is not what limits this network.
- **`ledger_bytes_delta` is still empty in every run** (as in rows 1–2): no producer for
  the column on this path. Ledger size is not measured here.
- **`negative-tests.csv` is absent in every run**: the `--repeat` driver does not run the
  Scenarios stage that writes it (same as rows 1–2). Listed in the copy set, absent for
  that reason.
- **One `go test` failure at the gate**, `TestSingleRunLockReturns409`: a `t.TempDir`
  cleanup race, pre-existing at `3cb07fc` (§1). Not a measurement-path defect; flagged
  for a saksi follow-up.
- **The session was interrupted once**: Docker Desktop and WSL were stopped mid-probe
  (c = 256 in flight). The interrupted folder `p2-sp-10k-c256-20260911-115949-1` (no
  `perf.csv`, no `run.end`) is kept in WSL and excluded everywhere; the network was
  rebuilt with `tier.sh 10000 1` and c = 256 rerun. Every run in §§5–7 is after the
  restart, on one Docker Desktop session.
- **`docs/manuscript-amendments.md` and `CLAIMS.md` were not edited.** What of this enters
  Table 3.12 and Chapter 4 is the user's decision.
