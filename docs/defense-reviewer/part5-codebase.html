Part 5: The Codebase, Saksi and BalotaChain

Everything in this part describes the code as built on 15 September 2026, at saksi commit 1812139 and balotachain commit a79918d, not the manuscript. Parts 1 to 4 tell you what the thesis promises; this part tells you where each promise lives in the repositories, what changed while building it, and where the code is weaker than the text. Paths are relative to each repository's root.

The two repositories and what each holds

  • Saksi (the framework): the saksi repository. Its packages hold the Rust cryptographic core, the Go chaincode and ledger client, and a Go research console that runs whole elections for the evaluation.
  • BalotaChain (the application): the balotachain repository. It holds the three web apps an operator, a trustee and the public use, and the thesis evidence under docs.

The manuscript calls Saksi a Rust library. The cryptographic core is exactly that. The saksi repository around it also carries the chaincode and the console, because the wire format, the on-chain verification and the evaluation harness are versioned together with the core and tested against the same vectors. If a panelist asks, say: the core is the library; the repository is the framework. Terminology still holds: Saksi is the framework, BalotaChain is the application.

Stage 5 is where code and manuscript differ most. Algorithm 4's per-precinct sub-accumulators were not built: with no on-chain accumulator there is no hot key to contend for, and the verifier recomputes every sum from the ballots. The change is written up in docs/manuscript-amendments.md; know that it exists before you defend Algorithm 4.

The research console behind Chapter IV

  • Single election: through the console's wizard or the admin app. Generate, check the data, encrypt and record, trustee ceremony, verify, then attack it.
  • Measurement campaign: warm-ups and measured repetitions of one configuration, summarised in summary.csv. Attacks are always off, because a security run perturbs timing.
  • Gates before a run: the validation ladder (1, 10, 100 and 1,000 voters) must have passed on the same build before any larger tier; the console also refuses a tier that will not fit the disk or memory, or whose longest phase would outlast the phase timeout.
  • Attack timeline: the lifecycle pauses before ballots, part-way through submission, after the close and during the ceremony. A PASS counts only when the attack was refused by the gate it targets; a refusal by any other gate is INCONCLUSIVE.
  • Resilience (T3): a fault stops the peer part-way through submission; resume submits only what the chain lacks and closes the election; verify-only reconciles the chain against the run.
  • Evidence per run: journal.ndjson (line 1 records the environment and commits), perf.csv, correctness.csv, negative-tests.csv, and a campaign export zip for the cost model.

This is your answer on traceability (Software development, pp. 42 to 44): every run folder names the saksi commit in run.json and in journal line 1, and a failed repetition is recorded with its reason rather than dropped.

Known soft spots in the code (know these before a panelist finds them)

  • Older runs used fixed DKG dealers. Runs made before saksi commit 1812139 have keys derivable from the source: cite them for correctness, verifiability and performance only (each run.json names its commit).
  • The ceremony is simulated. The generator produces every partial decryption and signature in one process, and the console forwards them when a trustee acts, so that process holds every key share. The cryptography is real; separation between trustees is not exercised.
  • No caller authorization in the chaincode. Anyone on the channel can call any function; the gates still apply to what they submit.
  • Ordering is not detected on-chain or by the verifier.
  • Chaum-Pedersen proofs are checked for presence on-chain. A share with a wrong proof is recorded and caught only by the verifier.
  • One machine. The test network's two organisations and single orderer run on one computer, so distributed trust between operators is not demonstrated.
  • No live voter. The Flutter app is not connected; the Tauri shells and the one-voter runner in crates are left over from the earlier demo and are not built by CI.
  • An open gap on the public board. Its download links still point at the admin-only export route, although the console already serves a public copy of the verification files.

The code is the strongest evidence you have. For every part of it, know whether it is implemented, demonstrated, or a stated limit, and say which before you are asked.
